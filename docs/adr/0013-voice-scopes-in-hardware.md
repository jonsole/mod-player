# The Voice scopes are captured and drawn by hardware, triggered like a real scope, with straight lines between samples and fading persistence

*Its colours changed with ADR-0016: the traces are white, and only the newest capture is shown for now (persistence off).*

The status screen shows four oscilloscope traces, one per Voice, in a 2 x 2 grid in rows 4-11 of the console (y 96..287), each 316 pixels wide and 96 tall (`hw/rtl/scopes.v`). (The first version had them four across, 155 wide and 192 tall; the owner found them too low resolution, and wide matters more than tall.) They come from Paula's own per-Voice output (each Voice's sample x volume, the values its mix is made of), copied to an output port when Paula mixes, so its audio is unchanged.

Each Voice triggers on its output crossing zero going up, as an oscilloscope does, so a steady note stands still on screen, and the crossing is in the middle of the scope, with as much before it as after (at first it was at the left edge; the owner wanted it centred). So a capture records from its start, one point every 256 colour clocks, into its slot as a ring of 316; once 158 points are in, the next rising zero crossing is the trigger (if none comes within 10 ms, notes below about 99 Hz, the capture goes on anyway), and it records up to the 158th point from the one at or after the trigger. The window, 316 points and 22.8 ms, starts 158 points before the trigger's point; the display reads the ring from there (one adder per slot, for the scope being drawn). A capture takes 22.8 ms plus the wait for the trigger. A Voice's output is held between Paula's sample changes, so points taken at a fixed spacing draw steps, which the owner didn't like (`tools/scope_preview.py` models the options on real Songs: fixed stride with steps, straight lines between samples, one column per sample). The capture instead draws the straight line joining each pair of consecutive sample changes, and the point at a column's time is the line's value there. It finds the changes by watching the output's value (a change within 64 frames of the last is held over until 64 frames have passed, and a Voice that doesn't change takes a point anyway after 64 frames if it is 0 and 1100 otherwise, so every capture finishes). When the next change arrives, an engine shared by the four Voices does the rest: a serial divider gets the slope (4096 x the change in value, over the frames between), a bit-serial multiplier the first column's offset, and then one column is written every system clock until the change's time is passed. The engine takes under 50 clocks a segment and serves the Voices in turn, so the worst case, all four Voices with a segment in the same frame, is done in about 170 clocks, inside the 256 (64 frames of at least 4 clocks) before the same Voice can have another; that is why changes must be 64 frames apart. A first version gave each Voice its own engine and no longer fitted: ISE's `map` crashed placing a design at 96% of the chip's slices once the SD card was added. The value is the output * 3 / 32 in 1/16 pixel, and the point is that >> 4: -48..47, drawn from the bottom row to the top, so a full-scale Voice fills the scope; points are stored in 7 bits. A capture takes as long as 316 columns at 256 clocks (80 000 colour clocks, plus the trigger wait), so the scopes update every two or three video frames.

At the owner's request the traces persist like a scope's phosphor: each Voice keeps a ring of 4 capture slots, and the screen shows the newest capture at full brightness and the two before it at three quarters and half brightness (at first half and a quarter; the owner wanted more persistence, and brighter fades cost nothing where more generations would cost about 400 LUTs each). The fourth slot is the one being captured into. When all four Voices finish a capture its slot becomes the newest; the screen takes it at the next frame, and a new capture starts only once the screen has taken the last one (the slot numbers cross the clock domains Gray coded), so the slot being written is never on screen. A column's four slots are read together, so drawing three generations costs no more reads than one. The firmware turns the scopes on with bit 0 of the console's control register, while the status screen is up, and labels them with their Voice numbers in the text underneath.

## Considered options

- **Firmware draws the scopes in text cells** (block characters): a 12 x 24 cell gives only a few levels, the CPU would have to copy hundreds of samples a frame across the bus, and the Replayer's timing has to come first.
- **One shared capture memory in block RAM**: all four Voices capture on the same colour clock, so one write port would need queuing; sixteen small distributed RAMs (Voice x slot, 512 x 7 each) take about 1500 LUTs, which the device has to spare (the analyser uses most of the block RAM).
- **Free-running capture (no trigger)**: simpler, but the traces roll and flicker.
- **Points at a fixed spacing, held between samples**: the simplest, and what the first versions did; the steps show on low notes.
- **One column per Paula sample**: no steps and no interpolation, but the time scale changes with the pitch, a capture takes as long as 316 samples do (a third of a second on a slow Voice), and the owner preferred a fixed time.
- **A smoothing filter before sampling**: rounds the corners of steps but leaves the treads.
- **A phosphor bitmap that fades pixel by pixel**: smoother decay, but 4 x 316 x 96 pixels at even 2 bits each is more block RAM than is left.

## Consequences

- `make console-test` checks every point the hardware writes against a model of the capture (in `hw/sim/console_tb.cpp`, with the same integer arithmetic, run on the Paula C model's Voice output), and every frame's scope pixels against a model of the drawing, all three generations. `scopes_tb` holds Paula's frames back so that each capture ends from 8 clocks before to 8 clocks after the screen picks its next slot, checking no capture ever writes a slot on screen and that captures keep coming.
- One engine serves four Voices: a segment takes under 50 clocks, four in a row 170, and a Voice's knots are at least 64 frames (256 clocks) apart, so it never falls behind. `scope_capture_tb` checks one Voice with the engine on random input (including knots just under and over 64 frames apart); `console_tb` checks all four sharing it against the Songs' real Voices.
- Scope traces are drawn over the console's text; anything the firmware puts in rows 4-11 shows only where there is no trace.
- While Paula is paused the capture waits, so the scopes freeze on the last traces.
- The slot memories carry `ram_style = "distributed"`: left to itself XST put seven of them in RAMB8BWERs, which ISE 14.7's bitgen mishandles (docs/board.md), and `build.bat` stopped the build.
